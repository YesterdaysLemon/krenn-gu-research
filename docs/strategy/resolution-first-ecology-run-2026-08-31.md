## Why the operating emphasis is changing

The repository has become very good at producing exact scoped leaves,
certificates, audits, evidence tests, and frontier updates.  That machinery has
prevented real claim inflation.  It has also made a small, impeccably packaged
result much easier for an autonomous worker to finish than a risky parent
theorem.

The current symptoms are:

- many workers can choose among numerous advertised next obligations without
  sharing one active proof spine;
- a parent attempt can justify more sibling work even when the parent route
  remains no closer to a global consumer;
- each worker is implicitly incentivized to leave a green PR, so packaging and
  audit work expand to fill research time; and
- source, detector, and local-obstruction programmes can each advance while
  their interfaces remain unproved.

For this run, the shared parent implication is the deliverable.  Individual
leaf count, node count, lines changed, green checks, and theorem numbering are
not progress measures.

## What counts as progress

The run succeeds only if it produces at least one of:

1. a proved source-to-detector parent edge and a valid named downstream
   composition;
2. an exact physical countermodel to the parent implication, triggering the
   repository's dedicated counterexample or route-refutation audit;
3. an exact no-go eliminating a proposed universal mechanism across the whole
   parent scope; or
4. a proved exhaustive reduction to strictly smaller typed obligations, with
   at least one of them discharged during the same run.

A new local chart, factor, rank census, support orbit, candidate list,
verifier port, audit-only PR, status reconciliation, Proof Bonsai feature, or
“precise open problem” does not satisfy this run's objective unless the
coordinator first shows that it is a necessary child in an exhaustive cover of
the active parent.

## Roles and dispatch

Use one shared parent statement and divide methods, not mathematical scope.

- **Spine owner:** freezes the exact proposition and one named downstream
  consumer, maintains the dependency argument, and rejects tasks that do not
  shorten that spine.
- **Constructive synthesis:** attacks the complete mixed GHZ equations for a
  witness-wide violation of the simultaneous Fitting-failure profiles.
- **Adversarial/countermodel:** independently seeks an exact physical witness
  to parent failure or a route-killing no-go; abstract rank modules and modular
  samples are controls, not counterexamples.
- **Detector interface:** tests the entire supplied package against one named
  downstream theorem and either proves the composition or proves the exact
  interface mismatch.
- **Integrator:** alone owns rebasing, certificate portability, hostile review,
  ledger/frontier/README updates, PRs, and current-main validation after a
  mathematical candidate exists.

Research workers should hand the integrator exact identities, scripts,
countermodels, or proof text plus a short scope receipt.  They should not each
manufacture an independently packaged theorem surface.

## Run phases

1. **Freeze the spine.** Recheck current truth, reconcile the candidate parent
   formulation against accepted `GLS4/5/8/20/21`, and name the downstream
   consumer before launching computation.
2. **Attack both truth values.** Run constructive and adversarial work in
   parallel on the same proposition.  Exact small models are welcome only when
   they decide a quantified mechanism or produce a liftable witness.
3. **Mid-run kill decision.** If a mechanism fails, stop polishing it and move
   to the strongest surviving mechanism inside the same parent.  Do not open a
   new research lane merely to leave a positive artifact.
4. **Consolidate once.** When a parent theorem, exact no-go, or exhaustive
   reduction exists, the integrator performs independent review and repository
   publication.  Otherwise preserve one honest run report and no theorem PR.
