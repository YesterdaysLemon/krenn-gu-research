## Nonblocking governance hardening

The audit also recorded five actionable follow-ups.  They do not invalidate
Stages 14–16 or block this navigation correction:

1. Batch authorization is policy-enforced rather than machine-authenticated:
   the validator accepts any nonempty `approved_by`, and a resolvable
   `base_sha` is not yet bound to ancestry plus approved source blobs or a
   source tree.
2. Stage 16's informational approval-time manifest SHA hashes raw Windows
   checkout bytes and therefore reflects CRLF line endings.  The canonical
   mapping hash remains portable and authoritative; a future batch-contract
   revision should hash a Git blob or canonical JSON instead.
3. The Stage 14 stale-command guard does not yet follow command-variable
   indirection and misses `cwd=str(ROOT)` in a destination package.
4. Older exact-head Tier-2 referee identities and final verdicts are not all
   persisted durably: PR discussions are empty and earlier stage reports retain
   prospective merge-gate wording.  This checkpoint records its own referee
   identities and exact reviewed commit, but the older provenance should be
   normalized in a bounded follow-up.
5. Historical batch `p4-components-stage3` retains an unresolvable
   `base_sha`; its executed mapping provenance is intact, but full historical
   batch-contract validation is not reproducible from the current object
   store.

These items should be handled as bounded governance stages and must not be
used to broaden a scientific claim or bypass exact-mapping review.
